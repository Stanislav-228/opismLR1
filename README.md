## Завдання 1. Складові URI

### 1.1. Розбір URI

| № | scheme | userinfo | host | port | path | query | fragment |
|---:|---|---|---|---|---|---|---|
| 1 | `http` | — | `www.se-201-01.lab` | `80` (за замовч.) | `/orders/media` | `limit=99&page=uk` | `comments` |
| 2 | `http` | — | `blog.se-201-01.lab` | `80` | `/media/` | `limit=%D0%BA%D0%B8%D1%97%D0%B2` | — |
| 3 | `http` | `user:pass` | `edge.se-201-01.lab` | `80` (за замовч.) | `/orders` | — | `results` |
| 4 | `https` | — | `www.se-201-01.lab` | `9443` | `/orders/../media` | — | — |
| 5 | `mailto` | — | — | — | `admin@se-201-01.lab` | `subject=orders` | — |

| № | Ім'я, що запитується в DNS | Заголовок `Host` | Ціль запиту (request target) |
|---:|---|---|---|
| 1 | `www.se-201-01.lab` | `www.se-201-01.lab` | `/orders/media?limit=99&page=uk` |
| 2 | `blog.se-201-01.lab` | `blog.se-201-01.lab:80` | `/media/?limit=%D0%BA%D0%B8%D1%97%D0%B2` |
| 3 | `edge.se-201-01.lab` | `edge.se-201-01.lab` | `/orders` |
| 4 | `www.se-201-01.lab` | `www.se-201-01.lab:9443` | `/orders/../media` |
| 5 | Запит не виконується: схема `mailto` не потребує DNS-запиту до MX у межах HTTP-запиту | — | — |

Декодоване значення параметра URI 2: `київ`. Послідовність `%D0%BA%D0%B8%D1%97%D0%B2` є UTF-8 percent-encoding слова «київ».

URI 5 не має складової `host`, хоча містить символ `@`: у схемі `mailto:` частина `admin@se-201-01.lab` є адресою в `path`. Для розбору `authority` потрібна конструкція `//` після схеми.

### 1.2. Перевірка після створення DNS-зони

Приклади HTTP-запитів для перевірки:

```http
GET /orders/media?limit=99&page=uk HTTP/1.1
Host: www.se-201-01.lab
```

```http
GET /media/?limit=%D0%BA%D0%B8%D1%97%D0%B2 HTTP/1.1
Host: blog.se-201-01.lab
```

```http
GET /orders HTTP/1.1
Host: edge.se-201-01.lab
Authorization: Basic dXNlcjpwYXNz
```

Значення `dXNlcjpwYXNz` після декодування Base64: `user:pass`.

Для URI 4 очікується помилка підключення до TCP-порту `9443`, якщо вебсервер не слухає цей порт. DNS-резолвінг і встановлення TCP-з'єднання — різні етапи: успішне отримання IP не означає, що сервіс доступний на потрібному порту.

Під час звичайного запиту клієнт може нормалізувати шлях `/orders/../media` до `/media`. З параметром `--path-as-is` curl надсилає вихідний шлях без попередньої нормалізації клієнтом; вебсервер може нормалізувати його вже під час обробки.

**Фактичний вивід `curl` у моєму середовищі:** додати після запуску стенду.

## Завдання 2. Проходження ієрархії вручну

Для домену `ns.se-201-01.lab` послідовність делегування має вигляд:

1. Кореневий сервер `10.53.0.2` повертає делегування зони `lab.` на `ns1.nic.lab`.
2. TLD-сервер `10.53.0.3` повертає делегування `se-201-01.lab` на `ns.se-201-01.lab`.
3. Авторитативний сервер `10.53.1.1` повертає остаточний A-запис.

Команди:

```bash
dig @10.53.0.2 ns.se-201-01.lab A +norec
dig @10.53.0.3 ns.se-201-01.lab A +norec
dig @10.53.1.1 ns.se-201-01.lab A +norec
dig ns.se-201-01.lab A +trace
```

| Сервер | Очікуваний статус | Прапорець `aa` | Очікувана відповідь |
|---|---|---|---|
| `10.53.0.2` | `NOERROR` | відсутній | делегування `lab.` на `ns1.nic.lab` |
| `10.53.0.3` | `NOERROR` | відсутній | делегування `se-201-01.lab` на `ns.se-201-01.lab` |
| `10.53.1.1` | `NOERROR` | присутній | `ns.se-201-01.lab A 10.53.1.1` |

Відповіді root і TLD є відсиланнями: секція `ANSWER` порожня, прапорець `aa` відсутній, а в `AUTHORITY` міститься NS-запис наступного рівня. У `ADDITIONAL` може бути glue A-запис, який дає IP-адресу сервера імен.

Glue-запис потрібний, коли сервер імен розташований усередині зони, яку він обслуговує. Без glue резолвер знав би ім'я DNS-сервера, але для отримання його IP мусив би знову звернутися до тієї самої зони, що створює циклічну залежність.

Авторитативною є відповідь сервера `10.53.1.1`: вона містить прапорець `aa` і остаточний запис у `ANSWER`. Запис NS на TLD-сервері є делегувальним записом батьківської зони.

**Фактичні виводи `dig` та TTL:** вставити з термінала після виконання команд.

## Завдання 3. Заповнення власної зони

### Конфігурація DNS-зони

Файл зони для `se-201-01.lab` повинен містити SOA, NS та записи відповідно до параметрів варіанта. Приклад фінальної конфігурації наведено наприкінці звіту.

Після зміни файлу необхідно збільшувати `serial` та перезавантажувати зону командою стенду `zone-reload`.

### Перевірка записів

```bash
dig @10.53.1.1 www.se-201-01.lab A +norec
dig @10.53.1.1 blog.se-201-01.lab A +norec
dig @10.53.1.1 mail.se-201-01.lab A +norec
dig @10.53.1.1 se-201-01.lab MX +norec
dig @10.53.1.1 se-201-01.lab TXT +norec
dig @10.53.1.1 edge.se-201-01.lab A +norec
```

| Запис | Очікуване значення | TTL |
|---|---|---:|
| `www` A | `10.53.0.80` (початково) | `45` |
| `blog` CNAME | `www.se-201-01.lab.` | `45` |
| `mail` A | `10.53.0.80` | `45` |
| `@` MX | `50 mail.se-201-01.lab.` | `45` |
| `@` TXT | `"lab-token=470b3560"` | `45` |
| `edge` A | `10.53.0.81` | `35` |

Порівняння рекурсивного резолвера та авторитативного сервера:

```bash
dig blog.se-201-01.lab
dig @10.53.1.1 blog.se-201-01.lab +norec
dig se-201-01.lab MX
dig @10.53.1.1 se-201-01.lab MX +norec
```

Авторитативна відповідь повинна містити прапорець `aa`. Рекурсивна відповідь зазвичай містить `rd` та `ra`, але не `aa`, оскільки резолвер повертає результат клієнту після рекурсивного пошуку або з кешу.

Запит A для `blog` повертає два записи: CNAME, що вказує на `www`, та A-запис цільового імені. Це дозволяє клієнту отримати IP-адресу за одним DNS-запитом.

Тимчасове додавання `@ IN CNAME www` повинно завершитися помилкою `CNAME and other data`. CNAME не може співіснувати з іншими типами записів для того самого імені. Вершина зони вже має SOA та NS, а в цій роботі також MX і TXT.

**Фактичний вивід `zone-reload`, `dig` та `zone-check`:** вставити з термінала.

## Завдання 4. TTL і видимість змін

TTL визначає, як довго рекурсивний резолвер може використовувати закешований запис без повторного звернення до авторитативного сервера.

Для запису `www.se-201-01.lab` початковий TTL становить `45` секунд. Після зміни IP на авторитативному сервері резолвер може продовжувати повертати стару адресу, поки не завершиться залишок TTL у кеші.

Формула прогнозу:

\[
\Delta t = R
\]

де `R` — залишок TTL у кеші на момент перезавантаження зони. Найбільша можлива затримка за початкового TTL дорівнює `45` секундам.

Приклад послідовності перевірки:

```bash
dig www.se-201-01.lab +noall +answer
```

1. Отримати стару адресу через рекурсивний резолвер, щоб запис потрапив у кеш.
2. Зафіксувати час і залишок TTL.
3. Змінити A-запис `www` на `10.53.0.81`.
4. Збільшити serial та виконати `zone-reload`.
5. Перевірити адресу безпосередньо на `10.53.1.1`.
6. Повторювати запит до рекурсивного резолвера, доки він не поверне нову адресу.

| Показник | Значення |
|---|---|
| Початковий IP | `10.53.0.80` |
| Новий IP | `10.53.0.81` |
| TTL | `45` с |
| Прогнозована максимальна затримка | `45` с |
| Фактично виміряна затримка | Заповнити за власним вимірюванням |

Якщо фактична затримка перевищує прогноз, можливі причини: цикл опитування запускався не безперервно, інтервал `sleep` збільшив час фіксації, а також вплинули час виконання `dig` і момент оновлення кешу.

Для міграції сервісу за великого TTL (наприклад, 86400 с) спочатку зменшують TTL, чекають завершення старих кешів, потім змінюють IP і лише після стабілізації повертають TTL до більшого значення. Старий сервер варто залишати доступним протягом перехідного періоду.

## Завдання 5. Негативне кешування

Негативне кешування зберігає інформацію про те, що запитане ім'я не існує (`NXDOMAIN`). Тривалість такого кешування визначається SOA зони відповідно до RFC 2308.

Для заданих параметрів:

\[
T_{negative} = \min(TTL_{SOA}, SOA.MINIMUM)
\]

\[
T_{negative} = \min(15, 60) = 15\text{ с}
\]

Отже, очікуваний час негативного кешування становить `15` секунд.

Перевірка до створення запису:

```bash
dig @10.53.1.1 new-fuebx.se-201-01.lab A +norec
```

Після цього необхідно звернутися до рекурсивного резолвера, створити потрібний A-запис у зоні, збільшити serial та виконати `zone-reload`. Резолвер може ще деякий час повертати закешований `NXDOMAIN`.

| Показник | Значення |
|---|---:|
| TTL запису SOA | `15` с |
| SOA `minimum` | `60` с |
| Розрахунковий негативний TTL | `15` с |
| Фактичний час | Заповнити після вимірювання |

Негативна відповідь кешується за політикою SOA, оскільки відсутній запис не має власного TTL. Авторитативний сервер додає SOA зони в секцію `AUTHORITY`, щоб резолвер міг визначити тривалість негативного кешування.

Якщо скрипт спочатку перевіряє ім'я, якого ще немає, він може створити негативний кеш. Одразу після створення запису скрипт може продовжувати отримувати `NXDOMAIN`. Щоб уникнути цього, не слід перевіряти нове ім'я через рекурсивний резолвер до його створення; якщо негативний кеш уже виник, потрібно дочекатися завершення його TTL або перевірити запис безпосередньо на авторитативному сервері.

## Завдання 6. Затримка пошуку імені

Мета завдання — порівняти час першого та повторного DNS-запиту і визначити, які сервери залучаються до пошуку.

| Тест | Ім'я | Очікуваний шлях першого запиту |
|---|---|---|
| A | нове ім'я у `se-201-01.lab` | авторитативний сервер `10.53.1.1`, якщо делегування вже в кеші |
| B | нове ім'я в `lab.` | TLD-сервер `10.53.0.3`, якщо делегування `lab.` вже в кеші |
| C | ім'я в неіснуючому TLD | кореневий сервер `10.53.0.2` |
| D | `www.se-201-01.lab` після очищення/перезапуску кешу | root → TLD → авторитативний сервер |

Повторний запит зазвичай обслуговується з кешу, тому його час має бути значно меншим.

Команди для вимірювання:

```bash
dig x14937.se-201-01.lab A
dig x14937.se-201-01.lab A

dig x25585.lab A
dig x25585.lab A

dig x29614.z374 A
dig x29614.z374 A

dig www.se-201-01.lab A
dig www.se-201-01.lab A
```

| Тест | Перший запит, мс | Повторний запит, мс | Сервери за журналами |
|---|---:|---:|---|
| A | Виміряти | Виміряти | `10.53.1.1` |
| B | Виміряти | Виміряти | `10.53.0.3` |
| C | Виміряти | Виміряти | `10.53.0.2` |
| D | Виміряти | Виміряти | `10.53.0.2` → `10.53.0.3` → `10.53.1.1` |

Резолвер кешує не лише кінцеві A-записи, але й NS-записи делегування та glue-записи. Тому нове ім'я всередині вже відомої зони не обов'язково потребує повторного звернення до root і TLD.

Root, TLD та авторитативний сервер додають власну мережеву затримку. Під час першого відкриття сторінки з ресурсами з кількох доменів браузер повинен виконати DNS-резолвінг для кожного нового доменного імені. Запити можуть виконуватися паралельно, але загальний час може визначатися найповільнішим DNS-ланцюжком. Повторні відкриття прискорюються завдяки кешуванню.

## Завдання 7. Інцидент: зупинка власного сервера

У цьому завданні перевіряється поведінка двох резолверів після зупинки авторитативного DNS-сервера `10.53.1.1` та завершення TTL запису `edge.se-201-01.lab`.

Перед зупинкою сервера необхідно закешувати запис на обох резолверах:

```bash
dig @10.53.0.53 edge.se-201-01.lab A
dig @10.53.0.54 edge.se-201-01.lab A
```

Далі за інструкцією стенду зупинити авторитативний сервер командою `named-stop`, зафіксувати час і після завершення TTL перевірити обидва резолвери з вимірюванням часу.

Приклад команд перевірки:

```bash
time dig @10.53.0.53 edge.se-201-01.lab A +time=30 +tries=1
time dig @10.53.0.54 edge.se-201-01.lab A +time=30 +tries=1
```

| Резолвер | Очікувана поведінка після завершення TTL |
|---|---|
| `resolver-a` (`10.53.0.53`) | Може завершити запит тайм-аутом або `SERVFAIL`, якщо не має механізму видачі застарілої відповіді |
| `resolver-b` (`10.53.0.54`) | За увімкненого `serve-stale` може повернути застарілий запис із малим TTL |

**Фактичні результати:** заповнити після виконання експерименту.

| Запит | Статус або тайм-аут | ANSWER, TTL | `real` |
|---|---|---|---|
| resolver-a, перший | Виміряти | Виміряти | Виміряти |
| resolver-a, другий | Виміряти | Виміряти | Виміряти |
| resolver-b | Виміряти | Виміряти | Виміряти |

### Постмортем

1. **Що сталося.** Авторитативний сервер зони `se-201-01.lab` (`10.53.1.1`) був зупинений. Після завершення TTL запису `edge` резолвери мали отримати актуальні дані, але сервер не відповідав.
2. **Вплив на клієнтів.** Резолвер без `serve-stale` може повернути помилку або завершити запит тайм-аутом. Резолвер із `serve-stale` може тимчасово повернути застарілу IP-адресу.
3. **Хронологія.** Записати фактичний час `named-stop`, час запитів, тривалість очікування та час `named-start`.
4. **Роль кешу.** Звичайний кеш перестає використовувати запис після завершення TTL. `serve-stale` дозволяє тимчасово використовувати прострочений запис, коли авторитативний сервер недоступний.
5. **Що слід змінити.** Для підвищення доступності доцільно налаштувати вторинний DNS-сервер у незалежному сегменті мережі та перевірити політику `serve-stale`.
6. **TTL застарілої відповіді.** Малий TTL обмежує час, протягом якого клієнти використовують застарілі дані.
7. **Повторні запити.** Однакові тайм-аути можуть свідчити про повторні спроби резолвера звернутися до недоступного NS до завершення тайм-ауту.
8. **Відновлення.** Після `named-start` потрібен час на запуск процесу та завантаження зон; іноді також впливає короткочасне кешування помилок.
9. **Коли `serve-stale` шкодить.** Під час планової міграції IP застаріла адреса може спрямувати клієнтів на старий сервер. Тому механізм корисний для аварійної доступності, але потребує обережності під час контрольованого перемикання.

## Фінальний файл зони

```bind
; Zone se-201-01.lab
; Після кожної зміни збільшити serial та виконати zone-reload
$TTL 45

@   15 IN SOA ns.se-201-01.lab. admin.se-201-01.lab. (
        2026112501 ; serial
        3600       ; refresh
        600        ; retry
        86400      ; expire
        60         ; minimum
    )

@       IN NS      ns.se-201-01.lab.
ns      IN A       10.53.1.1

; Записи варіанта 1
www     IN A       10.53.0.80
blog    IN CNAME   www
mail    IN A       10.53.0.80
@       IN MX      50 mail
@       IN TXT     "lab-token=470b3560"
edge 35 IN A       10.53.0.81

; Запис для завдання 5 додається під час виконання експерименту:
; new-fuebx IN A   10.53.0.80
```

> Для завдання 4 A-запис `www` тимчасово змінюється з `10.53.0.80` на `10.53.0.81`, після чого серійний номер збільшується. Для завдання 5 додається запис `new-fuebx` після перевірки негативного кешу. У фінальному стані зони залишити записи, які вимагає методичка.

## Висновки

Під час лабораторної роботи розглянуто структуру URI та зв'язок між доменними іменами й DNS-запитами. Простежено делегування DNS від кореневої зони через TLD до авторитативного сервера, досліджено відмінності між авторитативними та рекурсивними відповідями.

Створено приклад DNS-зони з A, CNAME, MX і TXT записами. Розглянуто вплив TTL на поширення змін, принцип негативного кешування NXDOMAIN, затримки під час проходження DNS-ієрархії та поведінку резолверів у разі недоступності авторитативного сервера.

Основний висновок: DNS-кешування зменшує затримки та навантаження на сервери, але може відкладати видимість змін і зберігати негативні або застарілі відповіді. Для надійної роботи сервісів необхідно правильно вибирати TTL, контролювати серійний номер зони, мати резервні DNS-сервери та перевіряти поведінку резолверів під час відмов.
